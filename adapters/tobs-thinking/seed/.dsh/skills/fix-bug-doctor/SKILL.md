# 根因排错

出处是用户提供的 fix-bug-doctor 工作流。本包不另设许可。目标是一次碰到原因，而不是再补一层症状。

## 先往上看

已经在叶子上改过两次还在犯，就离开当前文件。样式先看父级和全局布局。脚本先看调用方、启动顺序和入口。接口先看中间层、网关和配置加载。依赖先看版本和产物路径是不是真的存在。旁边有一份正常的同类东西，就把差异列出来。原因没定位之前，不要加压制症状的补丁。

## 八条判断

1. 状态按谁的键存。多份同时存在会不会串。取到的是这一份，还是最近的全局那一份。
2. 判定要用本质属性或对方明说的意图。不要用长度、标点、修改时间或残留会话当替身。
3. 收紧或新增一条路径时，先列出谁还走同一个入口。统一开关要接上同一层的全部成员。
4. 同一份数据只留一个真相来源。边界由掌握上下文的一方写死，不要交给模型临时发明分隔符。
5. 登录、下单、会话这类主路径不能被一个可选功能拖垮。
6. 先拿运行时证据。没有证据，只许列待证假设，不许写生产修复。
7. 上一轮自己改过的分支也要查。关掉一个功能时，把当时引入的旁路一起找出来。
8. 只在会通过的样本上验证，不算验证。没打过最可能失败的边界，就写成部分修复，不要写成已经根治。

## 五步

1. 失败复盘：此前每次修错在哪，共同盲点是什么。
2. 线索重梳：把现象和容易被跳过的层分开。
3. 根因：连续问至少三次为什么。表面问题是什么，真正的原因是什么。
4. 方案：为什么这次能碰到原因，会影响哪里。
5. 验证：怎样复现才算没了，为什么同类的正常路径不会犯，怎样回滚。

## 写码前必须停

方案和验证写完之后，展示拟改范围，停下来。对方原话是「开工」「按这个改」或「可以动手」才可以改生产代码。「你看着办」或「差不多」不算，改成两个具体选项再问。

没有控制台、网络或日志证据时，不要写生产修复。对方催着先改，仍然先给分析和计划。只测了会通过的样本，就标注未测的边界。证据和假说矛盾，丢掉假说。

收工时把教训交给 recall-and-memory：个别问题进当前 Bot 的私有记录；反复出现的习惯问题，脱敏并经批准后进共享记录。不要把私聊原文放进去。
